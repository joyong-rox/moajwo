# 파일 읽기·결과 만들기 메모리 예산 (환경별)

업로드한 원본을 읽을(파싱할) 때와 결과 Excel을 만들 때 backend 메모리가 가장 크게 늘어난다. 이 문서는 무엇을 어디서 거절하는지,
환경마다 한도를 얼마로 두는지, 그 근거가 된 측정값을 적는다. 한도는 모두 환경 변수로 바꾼다 (`backend/app/config.py`).

- **단위**: 크기 한도와 화면 안내는 **MiB**(2^20 = 1,048,576바이트)다. MB(10^6바이트)와 섞지 않는다.
  Render 무료 인스턴스의 메모리는 "512 MB"로 안내된다 (무료 정책은 바뀔 수 있어 전환 직전에 공식 문서를 다시 확인한다).
  이 값이 512MiB인지 512×10^6바이트(≈488MiB)인지 구분하지 않고, 예산은 더 작은 **488MiB**에 맞춘다
  (시험 컨테이너는 Docker `--memory=512m` = 512MiB로 돌렸다).
- **기준**: 메모리 한도를 넘어 컨테이너·프로세스가 죽는 것은 입력 거절이 아니다. 한도는 그 전에, 정해 둔 단계에서 안내와 함께 거절하도록 둔다.

## 한도와 거절 단계

| 한도 | 환경 변수 | 로컬·폐쇄망 기본 | Render 권장 | 막는 시점 | 안내 (화면에 그대로 보임) | 거절 뒤 남는 것 |
|---|---|---|---|---|---|---|
| 파일 하나의 크기 (올린 그대로, xlsx는 압축된 크기) | `MOAJWO_MAX_UPLOAD_MIB` | 50 | 10 | 저장하는 중 — 넘는 순간 중단 | 파일이 너무 큽니다 (최대 N MiB). | 기록·파일 없음 (쓰던 파일 지움) |
| xlsx를 풀었을 때 크기 | `MOAJWO_MAX_XLSX_UNCOMPRESSED_MIB` | 32 | 16 | 저장 뒤, 읽기 전 (압축 목록의 크기 합) | 압축을 풀면 X MiB라 읽지 않았습니다 (한도 N MiB). 시트를 나누거나 필요한 범위만 저장해 다시 올리세요. | '읽지 못한 파일' 기록과 원본 (기존 동작과 같음) |
| 칸 수 (모든 시트, 빈 칸 포함) | `MOAJWO_MAX_FILE_CELLS` | 800,000 | 400,000 | CSV는 읽는 중 (넘는 행에서 중단), xlsx·xls는 읽은 뒤 | 칸이 너무 많아 읽지 않았습니다 (…, 한도 N칸 — 빈 칸 포함). 시트를 나누거나 … | 위와 같음 |
| 한 칸의 글자 수 | 고정 32,767자 (Excel 한 칸 한도) | | | CSV 읽는 중 (xlsx·xls는 형식 자체가 넘을 수 없음) | N행에 32,767자가 넘는 칸이 있어 읽지 않았습니다 … | 위와 같음 |
| 파일 하나의 글자 수 합 (모든 칸의 글자 길이) | `MOAJWO_MAX_FILE_TEXT_CHARS` | 64,000,000 | 16,000,000 | 읽은 뒤, 값을 정리·분석하기 전 | 글자가 너무 많아 읽지 않았습니다 (모든 칸의 글자 N자, 한도 M자). 긴 글자가 반복되는 열·병합을 줄이거나 시트를 나눠 다시 올리세요. | '읽지 못한 파일' 기록과 원본 |
| 병합 범위의 넓이 (xlsx) | 칸 수 한도와 같은 값 | | | 읽기 전 (시트 XML의 병합 목록 — openpyxl은 병합 칸마다 객체를 만든다) | 칸이 너무 많아 읽지 않았습니다 (병합 범위만 N칸, 한도 M칸 — 빈 칸 포함). … | 위와 같음 |
| 시트 수 | 따로 두지 않음 | | | 칸 수·풀린 크기 한도에 포함된다 | | |
| 동시에 읽는 파일 수 (같은 파일·다른 파일 모두) | `MOAJWO_PARSE_SLOTS`, 기다리는 시간 `MOAJWO_PARSE_WAIT_S` | 1, 60초 | 1, 60초 | 읽기 시작 전 차례를 기다림 | 업로드: 다른 파일을 읽는 중이라 60초 안에 읽기를 시작하지 못했습니다 — 잠시 뒤 다시 시도하세요 (동시에 읽는 파일 수 한도 1개). 그 밖의 화면: 503과 `Retry-After: 10` | 업로드는 기록·원본을 지운다 (다시 올리면 됨) |
| 화면용 파일 보기 보관 (캐시) | `MOAJWO_VIEW_CACHE_MIB`, `MOAJWO_VIEW_CACHE_FILES` | 128MiB, 20개 | 32MiB, 20개 | 거절 아님 — 상한을 넘으면 오래 안 쓴 것부터 버림. 한 파일의 추정 크기가 상한보다 크면 보관하지 않고 매번 읽음 | | |
| 한 요청의 파일 수 | 고정 20 | | | 요청을 받을 때 | 한 번에 최대 20개까지 올릴 수 있습니다. | 없음 |

- 화면의 업로드 안내는 `GET /files/limits`로 지금 서버의 한도를 받아 그대로 보여 준다 (환경마다 다른 값이 화면에 맞게 나옴).
- 칸 수 한도는 xlsx·xls에서 **읽은 뒤** 확인한다. 그래서 읽는 동안의 메모리 상한은 xlsx는 '풀었을 때 크기'가, xls는 '파일 크기'가 정한다.
- 보기 캐시의 크기는 행·칸 객체의 추정 크기(`sys.getsizeof`, 긴 글자 반영)로 센다. 칸 수가 아니라 바이트로 센다.
- **글자 수 합이 따로 필요한 이유:** Excel은 같은 글자를 파일에 한 번만 저장하고(공유 문자열) 여러 칸이 가리키게 한다. 읽은 값을 정리(앞뒤 공백 제거)할 때 칸마다 사본이 생겨, 몇 KB짜리 파일도 수백 MiB가 된다 — 칸 수·풀린 크기 한도로는 막지 못한다 (로컬 Windows, 수정 전: 10.7KB xlsx(풀었을 때 185KB)의 32,000자 × 800칸을 읽는 동안 최고 98.8MiB · 아래 2026-10-25 측정: 약 170KB 파일이 512MiB 컨테이너를 메모리 부족으로 끝냄). 병합 범위도 작은 파일 하나가 수십만~수백만 칸이 될 수 있어 읽기 전에 넓이를 본다.

## 측정 (합성 자료, 파일 하나를 새 프로세스에서 읽음)

`diagnostics/scripts/memory_budget.py`. 숫자·짧은 글자·날짜가 섞인 8열 통계표 모양. 긴 글자 CSV는 한 칸 2,000자.
격리 러너(GitHub Actions ubuntu-24.04, Python 3.11.17, 4 CPU, 16GiB) — run 39908813140. 리눅스 값은 프로세스 자신의 최대 상주 메모리(VmHWM)다.
읽기 전 프로세스(앱 모듈 import 뒤)는 약 45.6MiB.

- 로컬 Windows(Python 3.12, PeakWorkingSetSize, 공유 PC라 작은 단계만): xlsx 풀었을 때 8.1MiB → 최대 111MiB,
  CSV 5.4MiB → 154MiB, 긴 글자 CSV 2MiB → 62MiB, xls 0.98MiB → 41MiB. 리눅스보다 10~20% 작다.
- 중단 기준: 한 단계의 최대가 `--stop-mib`(러너 1500MiB, 공유 PC 400~500MiB)를 넘으면 더 큰 단계를 돌리지 않는다.
  공유 PC에서는 운영을 멈추지 않고 작은 단계만 돌렸다.

## 환경별 예산

예산 ≈ 앱 기동 상태(컨테이너 약 95MiB) + 읽기 한 건의 증가분(형식별 최대) + 보기 캐시 상한 + 결과 파일 만들기(아래 장의 칸 수 예산) + 여유.

### Render 무료 (인터넷 시연, 외부 DB) — 488MiB에 맞춤

Render 대시보드의 환경 변수(Environment)에 넣는다:

```
MOAJWO_MAX_UPLOAD_MIB=10
MOAJWO_MAX_XLSX_UNCOMPRESSED_MIB=16
MOAJWO_MAX_FILE_CELLS=400000
MOAJWO_VIEW_CACHE_MIB=32
MOAJWO_PARSE_SLOTS=1
MOAJWO_MAX_FILE_TEXT_CHARS=16000000
MOAJWO_MAX_OUTPUT_CELLS=300000
MOAJWO_MAX_OUTPUT_TEXT_CHARS=48000000
MOAJWO_OUTPUT_SLOTS=1
```

| 형식 | 이 한도에서 읽기 한 건의 최대 증가분 |
|---|---|
| xlsx (풀었을 때 16MiB) | 약 160MiB |
| CSV (40만 칸에서 중단) | 약 80MiB |
| xls (10MiB — 칸 수는 읽은 뒤 확인) | 약 85MiB |
| 긴 글자 CSV (10MiB) | 약 57MiB |

예산: 95 + 160 + 32 ≈ 290MiB, 실측 누적 최대 317MiB (위 표, 동시 요청·캐시 포함). 488MiB까지 약 170MiB가 남는다.

### 로컬 운영·폐쇄망 (Docker Compose, SQLite·Ollama) — 기본값

컨테이너 메모리 제한이 없고(WSL2 가상 머신 안), 공유 PC에서 운영과 다른 작업이 함께 돈다. 기본값을 그대로 쓴다.

| 형식 | 기본 한도에서 읽기 한 건의 최대 증가분 |
|---|---|
| xlsx (풀었을 때 32MiB) | 약 320MiB |
| CSV (80만 칸에서 중단) | 약 160MiB |
| xls (50MiB — 칸 수는 읽은 뒤 확인) | 약 430MiB (가장 큼) |
| 긴 글자 CSV (50MiB) | 약 190MiB |

예산: 95 + 430 + 128 ≈ 650MiB (xls 최악), xlsx 최악 ≈ 545MiB. 이 PR 전에는 xlsx 풀린 크기 한도가 100MB(≈95MiB, 증가분 약 930MiB)였고
동시에 읽는 수에 제한이 없어 큰 파일 둘이면 약 2GiB까지 갈 수 있었다.
공유 PC의 사용 가능 메모리가 자주 1GiB 아래로 내려가면 `MOAJWO_MAX_UPLOAD_MIB=20`(xls 증가분 약 170MiB)으로 낮추는 것을 검토한다
(지금 운영에는 적용하지 않음 — 운영 변경은 별도 승인).

## 결과 파일 만들기 (묶기·통합) — 칸 수 예산과 중단된 실행 정리

묶기·통합은 결과 Excel을 메모리에 다 만든 뒤 저장한다. 그동안 원본(묶기는 넣는 모든 파일)도 읽어 둔다.
그래서 결과가 커지면 위의 읽기 한도와 상관없이 메모리가 늘어난다.

**측정 (격리 러너, 512MiB 컨테이너, Render 권장 읽기 한도, 3열 시트 10개를 묶음, 2026-10-23 run 39937719132):**

| 결과 행 | 결과 칸 (행 × 5 — '원본 행'·'행 종류' 두 열 포함) | 걸린 시간 | 결과 파일 | 누적 최대 |
|---|---|---|---|---|
| 20,000 | 100,000 | 3.8초 | 0.5MB | 141MiB |
| 50,000 | 250,000 | 9.0초 | 1.2MB | 220MiB |
| 100,000 | 500,000 | 18.1초 | 2.4MB | 333MiB |
| 150,000 | 750,000 | 26.4초 | 3.6MB | 423MiB |
| 200,000 (묶기 행 한도 300,000 안) | 1,000,000 | — | — | **메모리 부족으로 종료** |

- 결과 칸 1천 개당 약 0.45MiB (기동 상태 약 95MiB 위). 결과를 만드는 동안 다른 요청(실행 기록 조회·작은 파일 올리기)은 정상 응답했다 (14~189ms · 0.6~1.4초).
- 종료된 뒤에는 그 실행 기록이 **'실행 중'으로 남고 쓰다 만 임시 결과(`*.xlsx.tmp`)가 남았으며, 다시 띄워도 그대로**였다.

**그래서:**

| 한도 | 환경 변수 | 로컬·폐쇄망 기본 | Render 권장 | 막는 시점 | 안내 | 거절 뒤 남는 것 |
|---|---|---|---|---|---|---|

## '반복 파싱 30→0'의 조건 (P-01, 보기 캐시)

10개 파일 분석에서 서버가 원본을 다시 읽는 횟수 30→0은 **보기 캐시가 채워진 상태**의 값이다.
캐시가 비어 있으면(기동 직후, 상한을 넘어 밀려난 뒤, 다른 원본) 파일마다 한 번은 읽는다. 그 최초 비용은 위 컨테이너 표 9번처럼
풀었을 때 14.8MiB xlsx 하나에 약 6.5초이고, 같은 요청을 다시 하면 13ms였다.

## 남은 위험·재지 않은 것

- 결과 칸 수 예산은 묶기 3열 시트로 잰 값이다. 긴 글자는 결과 글자 예산이 따로 막는다. 글자 예산 값은 같은 긴 글자를 여러 칸이 가리키는 파일(공유 문자열)로 쟀다 — 칸마다 다른 긴 글자는 원본 읽기부터 더 커서 파일 하나의 글자 한도·풀린 크기 한도가 먼저 막는다 (D3a: 고유 3,000자 × 5,000칸 묶기 216MiB).
- uvicorn 프로세스를 여럿 띄우면 읽기 차례·캐시·결과 만들기 차례가 프로세스마다 따로라 최대가 그만큼 곱해진다 (지금 이미지는 1개).
- 결과 둘 이상이 메모리 부족 없이 끝난 사례(차례를 늘린 경우)는 잰 조합에서만 확인했다. 셋 이상 동시, 긴 글자 결과와 큰 업로드가 겹치는 경우는 재지 않았다.
- 누적 최대가 512MiB에 닿고도 끝난 사례(통합 2·3개)는 같은 조건에서 늘 끝난다는 뜻이 아니다 (페이지 캐시 회수에 기댐).
- xls는 칸 수를 읽은 뒤에야 알 수 있어, 칸 수 한도를 넘는 큰 xls도 파일 크기 한도 안이면 다 읽은 뒤 거절한다.
- Render "512 MB"의 정확한 바이트 수, Render 실제 인스턴스에서의 측정은 하지 않았다 (Render 실제 환경은 바꾸지 않음).
- 다시 재려면: `python diagnostics/scripts/memory_budget.py backend out.json --xlsx-mib 2,8,16 --csv-mib 5,10 --text-mib 5 --xls-mib 2,5`
  (xls 단계는 측정용 `xlwt`가 필요). 공유 PC에서는 작은 단계만, 큰 단계는 격리 러너에서.
