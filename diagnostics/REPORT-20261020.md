### 11.2 진단 도구 보완 (`78a69e2`)

1차 상태는 다음과 같았습니다.
- `diag_common.py`가 `assert URL.startswith(("http://127.0.0.1:8086", "http://frontend"))`로 주소를 검사했습니다.
  - 문자열 접두어 비교라서 `http://127.0.0.1:8086.example`이나 `http://127.0.0.1:80861` 같은 주소를 거르지 못합니다.
  - `assert`는 최적화 실행(`-O`)에서 사라집니다.
- `NU_URL`에는 제한이 없었습니다.
- Python 요청은 환경 프록시를 쓰고 리다이렉트를 그대로 따랐습니다.

보완한 내용 (`scripts/diag_scope.py` 한 곳):
- `DIAG_URL`은 `http://127.0.0.1:8086`, `NU_URL`은 `http://127.0.0.1:8888`(또는 `off`)만 허용합니다.
  - scheme·hostname·port를 정확히 비교합니다.
  - 사용자 정보·경로·쿼리·조각이 있으면 거절합니다.
  - 거절은 `ScopeError`로 합니다.
- Python 요청은 프록시를 쓰지 않고, 리다이렉트는 이어지는 주소가 범위 안일 때만 따릅니다.
- 브라우저는 같은 범위를 씁니다. 첫 요청은 `page.route`로, 리다이렉트 이후 요청은 듣지 않는 프록시(`127.0.0.1:9`)로 막습니다. 예외는 `<-loopback>,127.0.0.1:8086`입니다.
  - **발견:** Playwright가 덧붙이는 `<-loopback>`에 맡기고 `127.0.0.1:8086`만 예외로 두면, 허용 주소까지 프록시로 가서 막혔습니다. `<-loopback>`을 맨 앞에 두어야 허용 주소만 직접 연결됩니다(Edge 155에서 루프백 임시 서버로 확인).
- 운영 health 감시(`monitor.py`·`health_timing.py`)는 별도 경로입니다.
  - 고정 주소 하나에 GET만 보냅니다.
  - 프록시를 쓰지 않고 리다이렉트를 따르지 않습니다.
  - 진단 모듈을 가져오지 않습니다.
  - 진단용 쓰기 요청(시드·업로드)은 운영 주소로 보낼 수 없습니다.

### 14.2 판정기의 빈 검사 범위 (PR #15)

재현 (`round5/repro/`, 입력 `{"blocked_out_of_scope":[]}`). 수정 전은 깨끗한 `13fd08c` 작업 트리에서 UTF-8 출력 환경으로 실행했습니다.

| 입력 | 수정 전 | 수정 후 |
|---|---|---|
| `--suite ""` | **0 (전체 완료)** | 5 |
| `--suite ","` | **0 (전체 완료)** | 5 |
| `--suite " "` | 5 (알 수 없는 묶음 `' '`) | 5 |
| `--suite " , "` | 5 | 5 |
| `--suite nav` | 2 | 2 |
| `--suite transition`, `nav,transition` | 5 (없는 묶음) | 2 (측정 없음 → 미측정) |
| `--suite nav --partial ""` · `","` | — | 5 |

- 원인 두 가지:
  - `--suite`를 쉼표로 나누고 빈 항목을 버린 뒤 목록이 비어도 막지 않았습니다.
  - 판정은 고른 기준이 0개여도 공통 기준(범위 밖 요청 0건)만으로 전체 완료가 됐습니다.
- 목록 규칙 (`--suite`·`--partial` 같음):
  1. 쉼표로 나눕니다.
  2. 각 항목의 앞뒤 공백을 지웁니다.
  3. 빈 항목은 버립니다.
  4. 같은 항목은 처음 것만 남깁니다.
  5. 정리한 목록이 비면 사용법 오류(5)입니다.
- 판정 단계 방어: 함수(`judge`)를 직접 불러도 고른 기준이 0개면 `COMMON.no_criteria`가 입력 오류가 되어 불완전(2)입니다.
- 그대로 둔 것: `fix`·`nav`·`fix,nav`, 부분 검사(3), 오류·범위 밖 요청을 합칠 때의 보호
  - 예: `" nav , nav "`는 `nav`, `"fix,,nav,"`는 `fix,nav`로 판정합니다.

### 14.3 판정기 출력 인코딩과 도구 오류 종료 코드 — 검증 중 발견 (PR #15)

- **증상:** 5차 작업 중 첫 진단 시험 실행(기록 도구 없이)에서 7건이 실패했습니다. 기록 도구로 다시 실행하니 70건 모두 통과했습니다.
- **반복 통과로 끝내지 않고 두 실행의 차이를 찾았습니다.** 첫 실행만 `PYTHONIOENCODING=utf-8`이 없었습니다.
  - 그 조건으로 두 번 다시 실행했고, 두 번 모두 같은 7건이 실패했습니다(`round5/logs/pytest-diag-no-utf8-env-1·2`).
  - 원시 출력: 판정기 CLI(하위 프로세스)가 보고서 첫 줄의 '—'(U+2014)를 Windows 파이프 기본 인코딩(cp949)으로 쓰다가 `UnicodeEncodeError`로 끝났습니다. 그 결과 파이썬 기본 종료 코드 1이 나왔습니다.
  - **판정기에서 1은 '실패(제품 결함)'입니다.** 판정기가 죽은 것을 제품 결함으로 읽을 수 있었습니다.
  - 같은 이유로, 종료 코드 1을 기대한 CLI 시험 1건은 우연히 통과하고 있었습니다.
- **4차 13.6 '첫 실행 실패 5건'과의 관계:**
  - 대화 기록에 남은 4차 명령을 보면, 실패한 실행만 `PYTHONIOENCODING` 없이 돌렸습니다. 이어진 '통과' 실행은 모두 이 변수를 붙였습니다.
  - 4차 커밋 `13fd08c`에서 변수만 빼고 두 번 실행하니, 두 번 모두 4차와 같은 요약 줄 `5 failed, 56 passed, 3 warnings`가 나왔습니다. 변수를 넣으면 61개 모두 통과했습니다(`round5/logs/pytest-13fd08c-*`).
  - 유력한 원인입니다. 다만 4차 원시 출력이 없어 실패한 시험 이름까지 같은지는 확인할 수 없습니다. 그래서 4차 기록은 '원인 미확인'으로 둡니다(13.6 정정).
  - 4·5차의 실제 판정 실행은 모두 이 변수를 붙였습니다(명령 기록으로 확인). 그래서 그때 기록한 판정 종료 코드는 이 문제의 영향을 받지 않았습니다. README의 실행 순서도 맨 앞에서 이 변수를 내보냅니다.
- **수정:**
  - 판정기는 표준 출력·오류를 늘 UTF-8로 씁니다.
  - 판정기 자체 예외는 새로 둔 종료 코드 **4**로 냅니다. 판정 결과(1·2)와 섞이지 않게 하기 위해서입니다.
- **시험:**
  - CLI 시험은 출력 인코딩 환경 변수를 빼고 하위 프로세스를 띄웁니다. 그래서 시험을 띄운 방식과 상관없이 같은 조건으로 봅니다.
  - 실패 시험은 종료 코드와 함께 '실패(제품 결함) 있음' 문구도 확인합니다.
  - 보고서 경로에 폴더를 줘 쓰기에 실패하게 하고, 종료 코드가 4인지 확인합니다.

### 14.4 전환 묶음 판정 기준 (`--suite transition`)

- 실행마다 기준 두 개가 있고, 모두 필수입니다.
  - `TR.<실행>.static` — 정지 상태: 마지막 프레임이 활성이고 안정됐으며 기준 이상
  - `TR.<실행>.moving` — 전환 중: 활성이 된 뒤 모든 프레임이 기준 이상
- 결과:
  - 활성 프레임이 하나라도 기준 미만이면 **실패**입니다.
  - 비활성→활성 전환을 관측하지 못했거나 기록이 없으면 **미측정**입니다.
  - 마지막 프레임이 비활성이거나 안정되지 않았으면 정지 상태가 미측정입니다.
- 기준은 그 프레임의 글자 크기·굵기로 고릅니다.
  - 24px 이상, 또는 18.66px 이상이면서 굵기 700 이상: 3:1
  - 그 밖: 4.5:1
  - 반올림 전 값으로 비교합니다(예: 4.4999는 실패).
- 기준 수: 23개 실행 × 2 = 46개
  - 실행 목록은 판정기와 시험에 따로 적었습니다. 판정기가 그 실행을 모두 요구하는지 시험이 함께 봅니다.
