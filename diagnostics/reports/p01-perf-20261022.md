# 반복 파싱·목록 비용 측정 (P-01, 2026-10-22)

## 방식

- **구성:** 격리 backend(uvicorn, 127.0.0.1:8096) + main 빌드본 vite 미리보기(127.0.0.1:8086), Edge 155 headless
  - 새 데이터 폴더·새 계정·합성 xlsx를 썼습니다.
  - 모델 주소는 차단했습니다 (`OLLAMA_BASE_URL=http://127.0.0.1:9`).
- **측정 실행기:** 저장소 코드는 바꾸지 않았습니다.
  - `app.files.parse_file`을 감싸 서버 파싱마다 시각·시간·확장자를 기록했습니다. 분석·미리보기·검토·통합이 모두 이 함수를 거칩니다.
  - ASGI 감싸기로 요청마다 경로(쿼리 값 없음)·상태·처리 시간을 기록했습니다.
  - 서버 CPU 시간·작업 메모리는 프로세스에서 단계 전후로 읽었습니다.
- **자료:**
  - 300행×4열 파일 50개 (그중 25개 매핑 확정)
  - 검토 20개
  - 40,000행 파일 1개
  - 분석용 300행 파일 10개
- **비교:** main `adebb6c`(수정 전)과 `perf/view-cache-budget`(수정 후). 같은 스크립트·같은 자료입니다.

## 바꾼 것 (이 PR)

- **화면용 파일 보기 보관** (`mapping_review._VIEWS`): '최근 2개 파일'을 '칸 수 합계 300만 칸 이내, 최대 20개'로 바꿨습니다.
  - 최악의 보관 칸 수는 오히려 줄었습니다 (전에는 300만 칸 파일 2개까지).
- **바꾸지 않은 것:**
  - 키: 파일 번호·sha256 — 원본은 읽기 전용이라 내용이 바뀌지 않습니다.
  - 보관 값의 가림
  - 권한 확인: 꺼내기 전 `get_file_for`
- **무효화 조건:**
  - 파서 판·가림 규칙이 바뀌는 것은 배포(프로세스 재시작)뿐이라 보관 값도 함께 사라집니다.
  - 매핑·확정·개인정보 확인은 보관하지 않아 바뀌어도 다시 만들 필요가 없습니다.

## 정정 — 측정 해석 오류

- **처음 해석:** '홈에서 다른 화면에 갔다 오면 10개 중 8개를 다시 읽는다'고 해석했습니다.
- **실제:** 요청 기록의 파일 번호를 대조하니, 돌아왔을 때 조회한 8개는 처음 확인하는 파일(11~18번)이었습니다. 홈 흐름은 보관 크기와 상관이 없습니다.
- 이 PR의 효과는 위 분석 사례로 다시 쟀습니다.
- 첫 측정에서 '다음 10개' 단계가 요청 0건으로 나온 것도 측정 시점 문제였습니다 (시험 도구 오류). 별도 재현(새 계정, 25개)에서 10 → +10 → +5로 정상이었습니다.

## 남은 것 (구현하지 않음)

- **업로드 결과 재사용:** 업로드 때 읽은 결과를 화면용 보관에 바로 넣으면 첫 미리보기의 재파싱이 사라집니다. 다만 업로드 직후 메모리 사용이 늘어 이번에는 하지 않았습니다.
- **검토 만들기·자동화 실행:** 매핑 엔진(임베딩)과 검증을 요청 안에서 동기로 합니다. 큰 파일·여러 파일이면 응답이 길어집니다.
  - 백그라운드 처리를 하려면 작업 큐가 필요합니다. 프로젝트 원칙상 Celery/Redis를 쓰지 않으므로 설계 결정이 필요합니다.
- **운영 Ollama가 켜진 상태의 임베딩 호출 시간:** 측정하지 않았습니다. 운영이 꺼져 있고, 공유 PC 메모리로는 로컬 모델 실행이 어렵습니다.
