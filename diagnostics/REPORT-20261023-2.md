## 4. PostgreSQL 시험 복원 (지시 3장)

- 파일 내용 문자열로 모듈을 빼던 규칙을 없앴습니다. 직접 SQLite 연결은 앱과 같은 DB에 붙는 `db_rows`·`db_connect`·`db_dump`(conftest)로 바꿨고, SQLite 자체만 보는 시험에만 `@pytest.mark.sqlite_only("이유")`를 붙였습니다.
- **169개 노드별 표: [REPORT-20261023-2-pg-skips.md](REPORT-20261023-2-pg-skips.md)** — 156개 PostgreSQL 통과, 13개 SQLite 전용(빈 SQLite 파일에 마이그레이션을 실행해 읽음) → 대응 `test_migrations_postgres.py` (빈 PostgreSQL → head, 모델 차이 0, 기본 용어사전 자료가 SQLite와 같음, 기동 때 잠금·응답 없는 서버 제한 시간).
- 바꾸는 중 PostgreSQL에서 드러난 시험 쪽 차이 3건 (제품 결함 아님): `column` 예약어, `LIKE '%…%'`의 `%`, 시각이 글자 대신 시간대가 붙은 값.
- 지시가 꼽은 PostgreSQL 직접 확인 범위 — 가입·승인·권한·세션 무효화·최초 관리자 중복 방지(여러 프로세스 포함), 소유자별 접근, 검토 완료·다시 검사, 통합·묶기, 그룹 가림 충돌, 차단 요청 무변경, 관리자 변경, 이관·실패 복구 — 는 해당 시험 파일이 모두 PostgreSQL 실행에 들어갔습니다 (노드별 표).
- 전체 시험은 최종 코드 후보에서 한 번씩 (`9c3842b`에서 한 번, #41을 더한 `4c0960f`에서 한 번 — 새 수정이 있어 다시 돌림). 같은 결과를 숫자를 늘리려고 반복하지 않았습니다. 그 뒤 후보 변경은 이 보고서(#36)뿐입니다.
- 시험 수의 비율은 코드 커버리지가 아닙니다.

## 6. 무료 외부 DB — Neon Free 기준 (지시 6장)

- 무료 조건 (2026-10-23 공식 문서 다시 확인): Neon Free $0·카드 불필요·기간 제한 없음, 프로젝트당 저장 1GB(전체 20GB)·100 CU-시간·공개 전송 5GB, 5분 무활동 뒤 컴퓨트 정지(끌 수 없음), 되돌리기 이력 6시간(1GB 한도)·수동 스냅숏 1개, 한도 초과 시 컴퓨트 정지·쓰기 차단(자료는 지우지 않음). **영구 보존 보장이 아니므로 따로 받는 백업을 둡니다.** Render 무료 Postgres는 30일 만료라 쓰지 않습니다. Render Free 웹 서비스는 SSH·Dashboard Shell·one-off job·영구 디스크가 없습니다.
- 기본안 표·백업 위치(`backups/external-db/`, Git·공개 링크 제외)·세션 재로그인: `docs/EXTERNAL_DB.md` 2장.
- **원천 확보:** 현재 배포된 앱에는 DB 내보내기가 없고(내려받기는 용어사전 CSV·결과 파일뿐), Render Free에는 셸·SSH·one-off job이 없습니다. 내보내기를 넣으려고 재배포하면 그 재배포가 SQLite를 지웁니다. 이 저장소 기록에 Render DB 백업은 없습니다. → 소유자에게 검증된 백업이 없으면 **Render 계정은 전환 뒤 새로 만들고**, 결과 보고에서 '새로 만든 계정'으로 적습니다. 이미 사라진 계정을 복구했다고 하지 않습니다.
- **복구 증명:** 격리 PostgreSQL에서 `pg_dump` → 다른 빈 DB 복원 → 그 DB로 띄운 앱에 같은 계정 로그인·계정 수 같음·원본 그대로 (러너·로컬). 실제 Neon 백업 복원은 프로젝트 생성 뒤.
- **복구 대상:** PostgreSQL을 지원하는 앱 이미지 + 검증된 외부 DB 유지가 기본. 환경 변수만 되돌리는 SQLite 복구는 문서에서 뺐습니다 (실제 복원 위치·명령·파일 생존 조건이 검증되지 않음).
- **쓰기 경계:** 로그인부터 쓰기입니다 (세션·최근 로그인·실패 횟수). 전환 뒤 점검에 쓴 계정·시각·세션 수를 기록하고, 쓰기 재개 뒤에는 옛 백업으로 되돌려 새 계정·자료를 잃는 복구를 자동으로 하지 않습니다.
- **최종 전환 승인 자료(한 묶음):** 프로젝트·지역·판, 무료 조건 확인 날짜, 원천 스냅숏 식별자·sha256·보호 시점·보관 위치(또는 '새로 만들기' 결정), 이관 보고서, 복원 확인, 최종 앱 SHA·이미지, 중단 계획, 복구 절차, 새 쓰기 보존(백업 주기) — `docs/EXTERNAL_DB.md` 8-5.
- 계정 보존 성공을 파일 보존 성공으로 넓히지 않습니다 (업로드·결과 파일은 서버 디스크 — 410 안내, 파일 보존은 별도 후속).

## 7. 배포·롤백 (#30, 지시 5장)

### 10-2. 병합 방식과 최종 SHA

- **권장 (A): 후보 브랜치 `rc/review-20261023`를 main으로 병합하는 PR 하나.** 시험한 트리 그대로이고 충돌 해법이 이미 들어 있습니다. 각 PR의 커밋이 main에 들어가므로 GitHub가 각 PR을 병합됨으로 표시합니다.
- **(B) PR별 병합:** 위 표 순서. 쌓은 PR은 앞 PR 병합 뒤 base를 main으로 바꿉니다. 이 순서의 충돌(모의 병합으로 확인): #26 `test_integration.py`, #31 `config.py`, #41 `integration.py`·`main.py`, #34 `mapping_review.py`, #37 `Upload.tsx`, #30 `nginx.conf`·`nginx.render.conf`, #38 `main.py` — **양쪽 변경을 모두 살려** 후보 커밋의 해법과 같게 풉니다. 충돌 파일을 후보 내용으로 통째로 바꾸면 중간 단계에 뒤 PR의 코드가 먼저 들어와 backend를 불러오지 못하는 단계가 생깁니다 (모의에서 확인) — 중간 단계는 시험하지 않았습니다.
- 어느 방식이든 **병합 뒤 `git diff <최종 후보 SHA> main`이 비어야** 하고, `scripts/deploy.sh`의 승인 SHA는 **최종 후보 SHA**입니다 (보고서까지 같은 트리). 모의 병합에서 PR 19개(#36 제외)를 위 순서로 합친 트리는 후보 `4c0960f`의 트리 `d5c9b2f`와 같았습니다.
- **최종 후보 SHA**는 이 보고서를 담은 `rc/review-20261023` HEAD입니다 (파일 안에 자기 자신을 담은 SHA를 적을 수 없어 PR #36 본문에 적음). 그 앱 코드는 `4c0960f`와 같고, 차이는 `diagnostics/` 보고서·스크립트뿐입니다 (`git diff --stat 4c0960f <최종 후보>`로 확인).
